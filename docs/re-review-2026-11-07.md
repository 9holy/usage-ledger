## 结论

第二轮修复之后仍有可复现的问题，主要集中在并发写入、账号证据的竞争与恢复、乱序解析缓存，以及旧账本对异常数据的处理。本轮继续修改代码，并以“旧版实际失败、修复后实际通过”为依据记录结论，没有把通过现有测试等同于没有缺陷。

全部修复均保存在本地审阅分支，GitHub 远端尚未发布这些修改。最终本地提交、补丁重建结果和文件校验值记录在随附修复包的 verification-summary.json。

统计准确性的前提仍是来源事实可用。账号交叉匹配对已采集的两侧日志成立，不是提供方签名认证或官方账单逐笔核验。没有足够证据的数据保持未归属、未知或单独列示。

### 采集、乱序与并发一致性

| 编号 | 原问题及影响 | 修复后行为 | 主要代码 |
|---|---|---|---|
| C1 | JSONL 采集器先读游标，再等待写锁；等待期间其他进程已提交完整游标，旧采集器却可写回更小 offset。 | 读取游标、重放标记和升级状态之前先取得写事务，批次用量与游标一起提交。 | collector.rs |
| C2 | DeepSeek 在写锁外解析，等待期间更高代次或同文件追加已入库；旧快照随后仍可删除新请求。 | 写锁内重新核验权威代次、当前检查点和文件指纹，陈旧快照停止替换并等待重试。 | deepseek.rs |
| C3 | Codex 运行模式和计费证据各自提交，可能一半成功一半失败；旧游标还可能覆盖新游标。已分裂的两个游标在源库重建后会漏读认证证据。 | 两种证据、相关用量修补及两个游标置于同一写事务；在同一源读取快照中核验两个检查点，失配时重放。 | codex_mode_logs.rs、store.rs、billing.rs |
| C4 | store 拒绝旧事件覆盖新计数，但 parser 的 recent/pending 缓存仍接受旧值；后续局部事件可能复活旧输出，或使新旧格式无法配对而重复累计。 | 较旧且有明确时间的事件不能回退新缓存和待配对端点；可用缺失字段仍交给持久化合并处理。 | parser.rs、store.rs |
| C5 | 两条独立合法的局部记录补齐后，可能形成缓存大于输入、推理大于输出的不合法组合。 | 持久化前再次检查标准化父桶约束；失败时原记录、保存金额和统计汇总不变。 | store.rs |
| C6 | 周统计数值校验和汇总 SELECT 不在同一数据库快照，另一连接的提交可在两步之间绕过校验。 | 校验与投影在同一读取事务；当前报告读旧的完整快照，下一次报告才看见新提交并执行校验。 | weekly.rs |

### 旧账本的类型、精度与错误处理

| 编号 | 原问题及影响 | 修复后行为 | 主要代码 |
|---|---|---|---|
| L1 | 源库字段类型不合法时，多个读取位置用默认 0、空串或 NULL 掩盖转换错误。 | 错型显式失败；当前批次的账目、水位和身份变化一起回滚。合法可选 NULL 与缺列默认保持兼容。 | ledger_ingest.rs |
| L2 | 负数、超过 JavaScript 精确整数范围的 Token、跨行累计及 SQLite 整数提升为 REAL 可能被接受、显示为 0 或溢出。 | 检查原始存储类型、非负性、各计数与合计的 2^53 − 1 上限，写入使用检查算术，报告使用同一读取快照。 | ledger_db.rs、ledger_ingest.rs、ledger_query.rs、ledger_merge.rs |
| L3 | 已封桶先执行 SQL 加法、后检查，坏历史值可能先被 SQLite 强制转成合法数值，掩盖问题。 | Add 前检查保留历史，Add 后再检查聚合结果；不擅自把无法解释的历史改成新值。 | ledger_ingest.rs |
| L4 | 历史错误分类 JSON 解析失败被当成空分布，分类计数累加还可能溢出。 | 严格解析、非负与总量检查、checked_add；错误明确返回且保留历史。 | ledger_ingest.rs |
| L5 | total_rows_seen 可接受负数、超精度值，继续摄取时未检查加法。 | 读取、显示与累加均检查范围；失败不推进当前批次的进度。该字段仍表示扫描行数，包含重叠扫描。 | ledger_ingest.rs、ledger_query.rs |
| L6 | 错型时间桶可在范围过滤前被排除，呈现为正常空报告；极大统计天数可触发乘法溢出。 | 报告入口先核验时间桶存储类型；天数换算使用检查算术。非正天数保留原有“全部历史”语义。 | ledger_db.rs、ledger_query.rs、ledger_merge.rs |

时间桶的全表类型检查只在报告入口执行一次；每个摄取桶仍按主键前导 hour_bucket 范围校验，避免“每桶扫描全部历史”的退化。拒绝异常值不等于删除或自动修复无法证明的原始事实。

## 二、怎样验证“修好了”

### 冻结旧版执行反例

保留了以 038a4518 为生产代码的独立 headless 副本，只加入本轮回归，不混入修复实现。原生反例使用真实 parser、保存逻辑和 SQLite，WAL 并发测试使用两个真实连接以及确定性的等待或触发点。故障注入采用 SQLite 失败触发器，检查保存前后完整记录、金额 JSON、汇总与检查点。

本轮新增 34 项原生回归，在冻结的旧生产实现上执行结果为：**32 项因断言或实际溢出失败，2 项正向兼容控制通过**。两项控制分别验证合法可选 NULL/缺列仍可摄取，以及无法证明应更改的历史报价必须原样保留。修复后的 34 项全部通过。

失败涉及账号竞争与撤销、额度原子性、订阅回填及旧报价迁移、JSONL/运行模式/DeepSeek 并发、乱序缓存、删除后重新匹配、周统计快照，以及旧账本类型和数值边界。逐项名称及原始输出见修复包的 evidence/review3-baseline-results.json 和 evidence/review3-baseline-final.log。

基线与候选使用不同 Cargo 包身份，隔离共享构建缓存。曾检测到旧版重跑误用了同名候选二进制，已保存诊断、分离身份并重新编译；该次错误运行不计入基线结论。

前端新增的三个反例也在原组件上分别实际失败，修复后通过。基线日志中的断言失败与夹具开发期间的编译问题分开保存；编译失败不计作缺陷证据。曾纠正一条累计记录测试的前置断言：后端 request_count 是记录数，需结合 unitemized_records 解释，不能错误要求累计块完全不占记录数。修正前置断言后，旧代码在真正的计费分类断言处失败。

## 三、升级与历史数据

代理匹配检查点提升为 billing_proxy_seed_v4，严格计费核验检查点提升为 billing_strict_evidence_v3。旧成功标记不会跳过本轮更严格的竞争匹配与累计计费核验。原始报价仍由既有保存与恢复机制保留；新回归检查了报价 JSON 和 Token 守恒。历史报价修复只使用其自身保存的费率和金额，不查询新价格重估；不明来源、不同币种、金额不符、Token 不完整或原始报价冲突的记录保持原样，避免扩大修复范围。

本轮没有更换模型价格表、汇率或币种规则，没有新增网络付费请求，也没有读取用户真实凭据、私人用量日志或生产账本。测试的账号、日志、时间和金额均来自夹具。

可恢复的历史继续按已有原始文件和合法归档重放。若错误分类的证据仍在，重新核验可以修正；若来源与原报价都已丢失，无法凭当前汇总反推全部历史。旧账本中已被过去的错型归零永久抹去的值，也不能由本轮校验自动推回。

## 四、可用范围与仍未完成的外部验证

- 账号归属是已收集日志内的交叉匹配，不是提供方原生账单对账。缺证据、冲突、未知计费身份保持明确状态。
- 累计块保留已知总量，但没有充分区间依据时不分配到具体账号、请求次数、日期或实时速率。
- 订阅参考金额、API 参考金额和提供方实际扣费或剩余额度不是同一指标，不能把估算承诺为最终账单。
- 未对 Windows/macOS 安装包、完整 Tauri GUI、真实登录切换与提供方账单执行真机验收；这些不包含在本地通过数字内。
- 原有依赖锁未在本轮改变，本轮没有重复第一轮的联网依赖漏洞扫描。此前扫描结果不能当作未来持续无漏洞的保证。
- Vite 大 chunk 提示及已知 jsdom XHR 控制台诊断按最终日志如实记录，不把它们隐藏成“没有任何警告”。
- 原有来源限制仍适用：同时间戳的完整冲突按来源顺序处理；采样式文件重写检测不能保证发现任意未采样的中间修改；缺失的上游事实不能补猜。

这些边界不等于已确认缺陷被保留。上表中已确认且可复现的本轮问题均有修复与回归，没有作出“所有输入、所有平台永远无问题”的保证。
