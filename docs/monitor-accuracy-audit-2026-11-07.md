## 二、账号归属到底依据什么

### 主账号统计

当前代码读取的诊断字段中，没有已确认可与提供方 response ID 直接核对的标识。因此，“请求日志交叉匹配”不应被描述成提供方签名确认或账单逐笔对账。实现要求线程一致、输入/输出/缓存计数完整且一致、模型或请求模型相符、时间处于请求开始前 1 秒到完成后 3 秒的兼容区间，并且在已采集的两侧记录中双向唯一。

若缺少对应日志、记录有冲突、一个候选同时对应多个请求，应用保留为未归属。双向唯一只对实际收集到的数据成立；若外部丢失了一侧的某条日志，应用无法证明那些未被采集的事件不存在。

账号内部使用工具命名空间及原始账号身份，邮箱、昵称、套餐和掩码显示名不参与身份合并。同工具同展示名的账号追加匿名标识；回归还覆盖两个摘要末 11 位相同的情况，确保可以延长到完整摘要区分。切换第二个账号后的 key 和金额、顺序反转以及隐藏后的标签均经过验证。

### 必须成立的守恒关系

对相同工具、相同已知时间范围和相同记录集合：

```text
全局周期用量 = 各账号的请求交叉匹配用量之和 + 未归属周期用量
```

`creatorReference` 是未归属记录中按创建者整理的参考视图，不能再加到右侧，否则会重复。`unlocatedTotals` 没有足够的请求时间或区间依据，单独列示，不加入该周期等式。账号身份、订阅/API 计费方式、额度池归属是三个不同维度，不能相互代替。

账号月/周卡片现在表达的是账号用量参考，其中可以包含 API 使用；只有当前有充分证据的订阅部分才可能参与相应额度预测。Token 金额估算与提供方剩余额度百分比也不是同一种计量单位。

## 三、时间、Token 和未知值的统一口径

### 有日期范围与全部历史

周期使用半开区间 `[start, end)`。真实请求时间决定归属，文件修改时间和采集时间不能证明请求发生在该周期。`legacy_initial_cumulative` 与 `legacy_cumulative_delta` 可以提供已知的历史数量，但没有完整的逐请求区间，因此不作为精确时间序列、实时速度或完整请求数。

一组固定反例里，正确周期只有 `110` Token，旧逻辑纳入了时间未知和累计记录后得到 `1650`。修复后周期为 `110`；无法定位的四条记录共 `1980` 单列；全部历史在同一结束点保留五条记录共 `2090`，不会把未知记录丢掉或额外加两次。工具、模型、时间桶和会话明细使用同一规则。

### 未知值不是零

新增质量字段包括累计记录数，以及输入、输出、缓存读取、缓存写入的未知记录数。它们随新增、修正、移会话、删除和启动回填一起维护，投影查询与保存的会话合计保持一致。

- 明确记录为零，仍显示 `0`。
- 完全缺失，显示未知。
- 有部分已知 Token，显示已知小计并标记不完整。
- 有已观察输出但总体输出不完整，保留下界，不宣称精确 Token/s。
- 一条累计块计为一条存储记录；实际覆盖多少次请求未知。

当前数据结构保留 `requestCount` 的存储记录数含义，以兼容已有接口；前端在存在累计块时明确显示“记录/累计记录”，不会把该字段包装成可知的实际请求总数。

### 不同来源的 Token 定义

本轮核对了官方字段语义：Codex/OpenAI 的缓存读取已包含在输入中，推理 Token 已包含在输出中，不能再次相加；Claude 的原始 `input_tokens` 是未缓存部分，标准化输入须包括缓存读取和缓存创建。跨来源统计先标准化再汇总，缓存/推理的细分仍作为组成信息。

依据包括 [OpenAI Codex 的固定版本协议实现](https://github.com/openai/codex/blob/f5ac7a757e8f6f4fe922f3daab0fcaba02f1fa72/codex-rs/protocol/src/protocol.rs)、[对应流式响应测试](https://github.com/openai/codex/blob/f5ac7a757e8f6f4fe922f3daab0fcaba02f1fa72/codex-rs/codex-api/src/sse/responses.rs)、[OpenAI 用量可观测性说明](https://developers.openai.com/api/docs/guides/agents-api/observability) 和 [Claude Prompt Caching 文档](https://platform.claude.com/docs/en/build-with-claude/prompt-caching)。这些资料用于核对字段含义；本轮没有据此改写官方模型价格或推断最终账单。

DeepSeek Harness 也核对了[固定版本的官方用量投影](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/packages/llm/token-meter/src/usage-projection.ts)：同一次尝试的后续样本替换之前样本，重试才开启新的计数位置，未缓存输入和缓存读写分开。Antigravity 没有足够依据确认的缓存口径保持未知或已知下界，不能为了统一显示而补出精确总量。

## 四、旧数据迁移与可恢复范围

内部 request ID 的变更涉及请求表、原始 API 报价、API 分类集合、请求额度关联、实时观察点和已保存的解析游标。迁移使用 Immediate 事务：失败不提交半套关系，成功标记和数据同批提交。旧观察点按各自保存的会话迁移，不能一并改成最后幸存请求的账号或会话。

仍有原始日志的记录会按新身份重放并去重。原文件已删除但合法 `.zst` sidecar 仍在时，使用已有归档读取器，校验来源前缀，仅重读已提交 offset 内的完整记录；未提交尾部不进入恢复。新的身份恢复步骤保留原游标和未知扩展字段，不制造当前实时输出；如果还是更早的模式游标，随后既有的模式升级仍会按已声明字段重新序列化。恢复成功后才移除待重放标记；重复启动不重复累计。

如果旧版本已覆盖某条记录，且原始日志和可用归档都不存在，仅靠剩余总量或额度百分比无法恢复该请求的真实 Token、时间和账号。修复不能追溯制造这些证据。来自已清理诊断源的归属历史也按现有已归档事实保留，源不可用不直接当成证据撤销。

现存请求的冻结报价原样保留。若某请求及其报价早已被旧 ID 碰撞覆盖，来源重放能恢复 Token 和请求事实，但无法从客户端日志找回丢失的原报价；这类首次恢复的记录按当前 catalog 估算。任意未知 cursor 扩展的保留只保证于数据库命名空间迁移和新的现代归档恢复路径，普通追加和旧模式游标升级仍按已声明的 `ParserState` 字段序列化。

旧周期新增的可信来源列默认不可信，只有后续认证观察确认同一周期时才提升。旧会话合计新增的质量字段一次性回填；保留已有金额、Token、报价与未识别的 JSON 扩展字段。启动回填、重启、并发 schema 升级均有独立回归。
